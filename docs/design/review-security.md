# REVIEW: security

SUMMARY: Security review of the Student Hub design, covering the schema and the five domain designs. I read the design text only (read-only) and checked two lims-sotoy files to confirm that its deploy runs as root. The biggest risks come from contradictions between domains rather than from any single domain:
1. The attendance design lets a SCHOOL_ADMIN move the geofence, although auth D19 reserves that to SUPER_ADMIN.
2. The academic design has a second student lifecycle that claims a NISN when a DRAFT is created, which lets any school lock graduated students elsewhere out of their accounts, and it skips the password policy.
3. Job routes are split between /api/v1/internal and /api/internal; nginx does not block the /api/v1 ones.
4. Platform's Origin-only CSRF would remove the HMAC check that protects the refresh cookie from being planted by a sibling subdomain.

Other HIGH findings:
- Login throttling is keyed only on IP, while the login key (NISN) is effectively public. IPv6 rotation or distributed guessing bypasses it, and temporary passwords never expire.
- A single admin can change the bank account that SPP and top-up payments go to, with no notification.
- SUPER_ADMIN has no second factor and can alone create sponsor credit and refund it as cash.

MEDIUM findings cover:
- The /docs page loads an unpinned CDN script on the same origin as the cookie-authenticated API.
- Holidays have no defined endpoints, and adding a national holiday deletes attendance rows in every school.
- Duplicate-selfie and duplicate-proof checks compare sha256 of re-encoded bytes, which any edit defeats; the proof check also leaks across schools.
- The two-session student cap allows another phone to check in for a student.
- A school admin can create fake student accounts to drain sponsor balances through clicks.
- The single PM2 process runs bcrypt, PDF and XLSX parsing on its event loop, and the zip-bomb guard can be bypassed.
- Orphan uploads can fill the disk that MariaDB shares.
- Ad banners are public before anyone reviews them.
- The app and its deploy run as root on a VPS shared with other clients.

The design already handles several things well:
- Sponsor balance changes lock the sponsor row, use a sequenced ledger and a CHECK constraint.
- Top-up and payment approvals are compare-and-set.
- Refresh tokens rotate with reuse detection.
- An id from another school returns 404.
- Uploads are re-encoded and served with safe headers.
- Ad links allow only https or the app's own scheme.

- [HIGH] (Attendance / school settings: geofence privilege) The attendance design exposes GET/PATCH /api/v1/admin/school/attendance-settings to SCHOOL_ADMIN. That endpoint accepts latitude, longitude, geofenceRadiusM (up to 1000 m) and timezone, which contradicts auth D19 (only SUPER_ADMIN may edit location, geofence or timezone). A school admin, or anyone holding a stolen SCA password, can move the fence centre or widen it so remote check-ins are recorded as HADIR with no reportable anomaly: distanceM is measured against the new fence, and GEOFENCE_TOLERANCE is only LOW. Changing timezone shifts local dates and auto-ALPHA for the whole school. Auth rule 21 also does not require an AuditLog entry for a PATCH /schools/{id}.
  -> FIX: Remove latitude, longitude, geofenceRadiusM and timezone from every SCHOOL_ADMIN-reachable schema. SCA may only change the schedule minutes, tolerance and schoolDaysMask through PATCH /schools/{id}/settings (z.strictObject, so unknown keys return 400). Geofence and timezone changes are SUPER_ADMIN-only via PATCH /schools/{id}, always write AuditLog before/after, and notify all active admins of that school. Add School.geofenceUpdatedAt and show it on the anomaly and map screens. Integration test: SCA PATCH with latitude returns 400, and SCA PATCH /schools/{id} returns 403.

- [HIGH] (Student lifecycle / NISN claim (cross-tenant)) The same resource has two incompatible specs. Auth defines /students, /students/{id}/activate|status, /users/{id}/reset-password and /students/import; academic-spp defines /school/students, /school/students/bulk and /school/students/:id/reset-password, and its rules are weaker: (a) C3/C4 claim activeNisn when a DRAFT is created, and the claim releases a GRADUATED holder at another school, so any SCA can lock any graduated student in the country out of their account by typing that NISN into an empty draft; (b) C1 only checks initialPassword for 8–72 bytes, skipping checkPasswordPolicy, so NISN or birth-date passwords are allowed; (c) C6/C7 bump User.tokenVersion, which auth D4 deletes; (d) import is per-row there but all-or-nothing in auth. Even with auth D14 (claim at activation), activation still silently releases another tenant's graduated holder. The origin school is never told, and the student.nisn_release audit row, if written with the new school's schoolId, exposes the other tenant's student id and status through /audit-logs.
  -> FIX: Build only the auth-tenancy lifecycle: claim at activation, password policy, session revocation instead of tokenVersion, all-or-nothing import. Delete academic's create, bulk, status and reset duplicates; academic keeps list, detail, class and sppAmount. Add a route-coverage test asserting there is exactly one student-create route. When a GRADUATED holder is released: write the release audit under the holder's schoolId (the new school gets its own entry with no foreign ids), notify the origin school's admins and SUPER_ADMINs (append NotificationType NISN_RELEASED), rate-limit releases per school (e.g. 20 a day, after which SU approval is needed), and let SU reverse a release.

- [HIGH] (Auth / online password guessing on NISN logins) NISN is effectively public (printed on school documents and searchable on Kemdikbud's public NISN lookup), so the password is the only secret. Throttling is keyed only on IP: LOGIN_PAIR uses 'ip::identifier' and LOGIN_IP uses 'ip'. (a) Rotating IPs, which is trivial over IPv6 because X-Real-IP is the full /128, gives unlimited guesses against one account and allows spraying common passwords across every NISN of a school. (b) Once the map reaches RATE_LIMIT_MAX_KEYS it drops the oldest keys, so flooding with unique keys can evict an active lock. (c) Auth D17 lets an SCA type initial passwords (in practice one default for the whole school), and temporary passwords never expire, so accounts nobody has activated stay open with a password the admin knows.
  -> FIX: In clientIp, normalise IPv6 addresses to their /64 prefix before building keys. Add an identifier-only limiter, 'login:id:<identifier>' (e.g. 10 failures in 15 minutes locks for 15 minutes, with progressive delay), that does not depend on IP, plus an alert on the global login-failure rate. The sweep must never evict a key that has an active lock; if the map is still full, return 429 for new keys. For STUDENT accounts allow only generated initial passwords (typed passwords stay allowed for staff). Add User.tempPasswordExpiresAt (e.g. 14 days) on create and reset; a login with an expired temporary password returns 403 TEMP_PASSWORD_EXPIRED until an admin resets it.

- [HIGH] (SPP / top-up bank account (payment-redirection fraud)) Any SCHOOL_ADMIN can edit School.bankName, bankAccountNumber and bankAccountHolder, the account shown to students for SPP transfers, through two endpoints: auth PATCH /schools/{id}/settings (no audit required) and academic PUT /school/billing-settings. Any SUPER_ADMIN can edit PlatformSetting.topUp*. A rogue admin, or a stolen password-only admin login, swaps the account number and every parent or sponsor then transfers money to the attacker. The uploaded proofs look genuine, and no one is notified of the change.
  -> FIX: Keep one endpoint for the school bank fields. Make the change two-step: the SCA writes School.pendingBank* plus pendingBankRequestedAt/By; a SUPER_ADMIN approves it, or it applies after a 24-hour cooling-off that can be cancelled, and only then does /me/payment-info show it. Always write AuditLog before/after and notify every active SCA of the school and every SU. For 14 days after a change, /me/payment-info and invoice detail carry 'rekening tujuan berubah pada <tanggal>'. PlatformSetting.topUp* follows the same rule, plus step-up re-authentication, and notifies all SUs and sponsors.

- [HIGH] (Super admin / sponsor ledger money controls) SUPER_ADMIN logs in with a password only (no MFA, 7-day web session) and alone can: approve top-ups (creating balance), post an ADJUSTMENT of up to ±Rp100,000,000 per entry, and post a REFUND (real money paid out to the sponsor) with only a note. A positive ADJUSTMENT can later be refunded, so one SA, or one stolen SA session, can turn made-up credit into a real bank payout. The sponsor design also lists no AuditLog write for ledger adjustments or for top-up rejection.
  -> FIX: Require TOTP for SUPER_ADMIN (User.totpSecretEnc encrypted with a separate key, User.totpEnabledAt). Require step-up (TOTP within the last 5 minutes, recorded in AuthSession.stepUpAt) for: top-up approval, ledger ADJUSTMENT and REFUND, platform bank settings, geofence edits, creating a SUPER_ADMIN, and resetting another SA. Cap REFUND at the refundable balance, Σ TOPUP − Σ CLICK_CHARGE − Σ REFUND (positive ADJUSTMENTs are never refundable), as a pure rule in ledger-rules.ts with tests. REFUND and any ADJUSTMENT above e.g. Rp1,000,000 need approval from a second SA (a LedgerAdjustmentRequest row in PENDING). Call writeAudit for ledger.adjust, ledger.refund and topup.reject.

- [MEDIUM] (Internal job endpoints) Job routes are specified four different ways: auth /api/v1/internal/jobs/auth-cleanup (X-Job-Secret plus no X-Real-IP), sponsor /api/v1/internal/jobs/ads-banner-gc and /ads-reconcile (secret only), attendance /api/internal/jobs/auto-alpha with 'Authorization: Bearer $CRON_SECRET', and platform /api/internal/jobs/{job} with X-Job-Secret. nginx only blocks '^~ /api/internal/', so the /api/v1/internal routes are reachable from the internet, and ads-reconcile writes data (it rebuilds AdDailyStat). CRON_SECRET is missing from the env schema and the .env template, so an unset secret risks comparing against an empty or undefined value. A Bearer cron secret collides with getAuth, which treats every Bearer header as a JWT and never falls back. The /api/v1 job routes would also appear in the OpenAPI document.
  -> FIX: Use one route, src/app/api/internal/jobs/[job]/route.ts, dispatched from jobs/registry.ts and tick. Use one JOB_SECRET (required by zod, at least 32 characters, checked at boot) sent only in X-Job-Secret, compared in constant time, returning 404 on failure. Reject any request that carries X-Real-IP: nginx always sets it. Do not use the socket address as the loopback check, because nginx also connects from 127.0.0.1. Guard tests: no route file under src/app/api/v1/internal, and no /internal path in the OpenAPI document.

- [MEDIUM] (Web auth / CSRF, refresh-cookie tossing, missing secrets) Auth D6 (per-session HMAC CSRF token plus Origin plus Sec-Fetch-Site) conflicts with platform D17/H7 (Origin or Sec-Fetch-Site only, 'no token dance'). The Origin-only version is unsafe for /auth/refresh. The refresh cookie is '__Secure-sh_rt' with Path=/api/v1/auth, and unlike a __Host- cookie, a __Secure- cookie can be set with Domain=.<parent> by any sibling subdomain; this VPS hosts other client apps (lims) that may share the parent domain. A compromised sibling plants its own refresh token with a more specific Path. The victim's same-origin refresh passes the Origin check and moves the victim into the attacker's session, where, for example, a sponsor then uploads a top-up proof into the attacker's account. Only the HMAC(sid) check in auth rules 5 and 6 blocks this. Separately, CSRF_SECRET and AD_EVENT_SECRET are required by the auth and sponsor designs but are missing from the platform env schema, the VPS .env template and the CI env.
  -> FIX: Make auth D6 the only CSRF implementation, inside defineRoute (token plus Origin plus Sec-Fetch-Site), and keep the HMAC check on /auth/refresh and /auth/logout. Reject any request that carries more than one '__Secure-sh_rt' cookie: return 403 and clear it. Add CSRF_SECRET and AD_EVENT_SECRET (at least 32 bytes each; JWT, CSRF, AD_EVENT and JOB secrets must all differ) to env.ts, the .env template and CI, and fail boot if any is missing. Prefer a domain that other apps' subdomains do not share.

- [MEDIUM] (API docs page (/docs)) Scalar is served at /docs on APP_ORIGIN and loads its bundle from cdn.jsdelivr.net; the @scalar/nextjs-api-reference default points at @scalar/api-reference without a version, so it always gets the latest release. Auth rule 6.4 makes this page read '__Host-sh_csrf' and send cookie-authenticated requests. If that npm package or the CDN is compromised, the script runs on the same origin with the full session and CSRF token of whoever opens /docs, typically a SUPER_ADMIN. The production Basic auth does not help, because the attacker is the script, not the visitor.
  -> FIX: Serve the docs on a separate origin (e.g. docs.<domain>) that the session cookies never reach, and use Bearer-only 'Authorize' there with the token pasted in. Alternatively, self-host a pinned bundle from node_modules with no CDN, and send a CSP on /docs of script-src 'self' and connect-src 'self'. Either way, remove the cookie-reading requestInterceptor from rule 6.4.

- [MEDIUM] (School calendar / Holiday (cross-tenant data deletion)) No domain defines Holiday endpoints, yet attendance 3.8.6 hard-deletes AUTO_ALPHA and LEAVE attendance rows whenever a holiday is added, and for a national holiday (schoolId NULL) it does so across every school. If the unspecified create schema takes schoolId, or allows it to be null, from the request body, a SCHOOL_ADMIN can create a national holiday and wipe rows in every tenant. Even within one school there is no backdating limit: an SCA can add a year-long retroactive holiday and permanently erase ALPHA and leave history, because removing the holiday restores only the last 7 days through the auto-ALPHA lookback.
  -> FIX: Define /school/holidays for SCA, with schoolId taken only from resolveSchoolScope and a strictObject body that has no schoolId field. Define /platform/holidays for SU only, for national holidays with schoolId NULL. Limit SCA backdating (e.g. startDate ≥ today − 7); anything older needs SU. Replace the hard delete with a soft void (e.g. Attendance.voidedByHolidayId) so that removing a holiday restores the rows, and write an audit entry with row counts. Tests: an SCA request with schoolId:null returns 400; a holiday of another school returns 404.

- [MEDIUM] (Selfie and payment-proof reuse detection) DUPLICATE_SELFIE, PROOF_ALREADY_USED and duplicateProofOf all compare the sha256 of re-encoded bytes, and Attendance.selfieFileId @unique only stops the same StoredFile row being used twice. Any crop, rotation, one-pixel edit, screenshot or re-save changes the hash. A student can therefore reuse one selfie every day, and a family can reuse one transfer screenshot across months or siblings, without detection. In addition, the platform S6 duplicate join and the academic D15 409 are not limited to one school: an SCA review screen can reveal another school's matching submission, and a student gets a cross-tenant 'this image exists' oracle.
  -> FIX: Compute a 64-bit perceptual hash (dHash: sharp greyscale resize to 9×8) at upload and store StoredFile.phash Char(16) with an index on (kind, schoolId, createdAt). Selfies: raise DUPLICATE_SELFIE (HIGH) when the Hamming distance is ≤ 6 against this student's selfies from the last 60 days or any same-school selfie from the same day. Proofs: flag near-duplicates within the same school for the SCA and never reject automatically; show cross-school matches only to SU. Remove the global 409 PROOF_ALREADY_USED, or limit it to the same student.

- [MEDIUM] (Attendance fraud / proxy check-in) MAX_ACTIVE_SESSIONS.STUDENT = 2 lets a student stay logged in on a friend's phone while the friend checks in for them at school. The friend's phone sends its own consistent deviceId, so DEVICE_SESSION_MISMATCH never fires. DEVICE_CHANGED is LOW, so it never reaches the review queue. SHARED_DEVICE is avoided by a modified client that sends a different deviceId, since every field is client-supplied. The selfie is not face-verified.
  -> FIX: Allow one live mobile session per STUDENT: a new login revokes the old one with reason REPLACED. Record Student.boundDeviceId and deviceBoundAt. For 7 days after a device change, flag check-ins NEW_DEVICE (MEDIUM, reportable), and notify the SCA when a student changes device more than twice in 30 days. Reject, rather than flag, a check-in whose deviceId differs from the session's deviceId. Put Play Integrity and App Attest on the roadmap as the real fix, and document that the selfie only supports manual review.

- [MEDIUM] (Ads / click fraud with fake student accounts) A click is billable when the student is ACTIVE and has changed their password. Any SCHOOL_ADMIN can create unlimited students, since made-up data passes activation, and can reset their passwords. Every student account can bill each ad once per WIB day through a scripted POST /student/ads/clicks; no impression is required, because tokens come straight from GET /student/ads. A rogue or compromised SCA, or a competitor who controls accounts, drains a sponsor's balance at CPC × accounts × ads per day. The ads-reconcile job only checks the arithmetic, not fraud.
  -> FIX: Record the click but do not charge it (append ClickBilling value SUSPECT) when any of these holds: Student.activatedAt is less than 7 days ago; the student has no CHECKIN attendance in the last 14 days; or no impression for (userId, adId) is in the dedupe store within the 30 minutes before the click. Add a cap on charged clicks per (ad, school, WIB day), e.g. 20% of that school's active students. Have ads-reconcile flag schools whose CTR is more than 3× the platform median, so SU can refund through ADJUSTMENT.

- [MEDIUM] (Availability: CPU work on the single fork process) The whole platform runs as one PM2 fork process, yet heavy work on untrusted input runs on its event loop: a bcryptjs (pure JS) cost-10 compare on every login attempt, including DUMMY_HASH for unknown identifiers; exceljs parsing of 1,000-row imports plus 1,000 cost-6 hashes; and pdf-lib parsing and rebuilding of 5 MB PDFs. A distributed login flood (limits are per IP) or one crafted PDF or XLSX can stall 07:00 check-ins for every school. The XLSX zip-bomb guard trusts the uncompressed sizes declared in the central directory, which an attacker can forge. PDF handling is also inconsistent: academic D15 serves raw, un-rebuilt PDFs to admins' desktop readers, and pdf-lib copyPages copies fonts and image streams verbatim, so exploit payloads aimed at PDF readers survive the rebuild.
  -> FIX: Run bcryptjs, XLSX parsing and any PDF handling in a worker_threads pool (e.g. piscina) with resourceLimits, a per-task timeout and a bounded queue; when the queue is full, return 503 SERVICE_UNAVAILABLE. bcryptjs stays the library. Enforce the 25 MiB zip limit while inflating, by counting actual output bytes. For v1, accept images only for PAYMENT_PROOF, TOPUP_PROOF and LEAVE_ATTACHMENT, which attendance and sponsor already chose (banking apps can export screenshots), and drop academic D15's raw-PDF path. If PDFs are needed later, rasterise them to JPEG inside the worker.

- [MEDIUM] (File storage / disk exhaustion) The two-step upload (POST /api/v1/files, platform D8) keeps orphan files for 24 hours. The limit is 30 uploads per 10 minutes per user, each up to 10 MiB in and roughly 1 MB stored for proofs, so one student account can keep about 4 GB of orphans on disk at all times. A handful of accounts can fill the 54 GB disk that MariaDB and lims also use, taking the database down for every tenant.
  -> FIX: Cap unattached files per user (e.g. at most 5 files and 20 MB; beyond that return 429), and add a daily cap on stored bytes per user. Refuse uploads with 503 when free disk space falls below 5 GB. Set the orphan TTL for ATTENDANCE_SELFIE to 1 hour, since the selfie max age is 10 minutes anyway, or keep the single multipart check-in request so no selfie orphans exist. Put STORAGE_ROOT on a separate filesystem or quota from the MariaDB data directory.

- [MEDIUM] (Ad banners in the public bucket) AD_BANNER files are written to the public bucket at upload time and served by nginx at /media/ with immutable caching. PENDING sponsors may upload (sponsor D1), and canReadFile allows AD_BANNER to any authenticated user. Images nobody has reviewed, including banners of DRAFT or REJECTED ads, which the orphan cleanup never removes, are publicly hosted on the school platform's domain. That makes the domain available for inappropriate images or online-gambling ('judi online') promotion, content that is especially damaging next to minors.
  -> FIX: Store banners in the private bucket. Before approval, serve them only through /api/v1/files/{id} to the owning sponsor and SUPER_ADMIN. When an ad is approved, copy its banner to a new public key; delete the public copy on takedown, rejection or archive. The imageUrl returned by ad serving always points to the approved public copy.

- [MEDIUM] (Deploy / VPS isolation) VPS setup and cron run as root. The deploy script writes to /root/backups/studenthub, so VPS_USERNAME must be root, as it is in lims deploy.yml. pm2 startOrReload therefore runs the Next app as root. Any remote code execution in the app, whether through an image or PDF parser bug or a compromised dependency installed during deploy, becomes full root on a VPS that also hosts other clients' production apps and databases. The deploy key stored in GitHub secrets is a root key.
  -> FIX: Create a 'studenthub' system user that owns /www/wwwroot/studenthub and /www/wwwroot/studenthub-storage. Run PM2 (with its own PM2_HOME) and the deploy SSH session as that user. Run DB backups from a separate root cron, or with a backup-only MariaDB user (SELECT, LOCK TABLES, SHOW VIEW, TRIGGER) writing to a directory the app user owns. Give nginx read access to storage/public through group permissions only. Restrict the deploy key in authorized_keys with no-port-forwarding, no-agent-forwarding and no-X11-forwarding.

- [LOW] (Personal data of minors) (a) CheckInRejection keeps the exact latitude and longitude of rejected attempts, often a minor's home, for 90 days and plots them on the admin map (includeRejected). (b) GET /student/attendance/today sends the exact geofence centre to the client, which hands spoofers their target. (c) mapError logs full error messages: Prisma validation and unknown-request errors echo the query arguments (name, NISN, address, guardian phone, even passwordHash) into PM2 logs. (d) Selfie retention is inconsistent: 90 days in the attendance design, 180 days in the platform design.
  -> FIX: For rejections store distanceM and accuracyM, with coordinates rounded to 3 decimals (about 100 m) and no coordinates at all beyond 2 km. Return only the radius and the student's computed distance, not the centre. Log Prisma errors as {name, code, meta.target, requestId} only, never .message, and add a test that PII does not appear in the log output. Use a single SELFIE_RETENTION_DAYS constant, the shorter 90 days, until the client answers.
