# Kritik adversarial — N2-notification-categories

Verdict: Not ready to execute: implemented as written, the missing case for the new CHECK constraint turns `pnpm test:int` red. Three more fixes are needed: re-derive categories, hints and the ENUM list after B1/A1 and settle the N4 category decision; resolve the PLAN.md:161 PRIMARY_ADMIN_PROTECTED conflict; fix the minor UI and DTO wiring issues. The core design (write-time filtering in notifySchoolAdmins, user AppLock, audit in the same tx, SYSTEM never muted) is sound and matches the code.

1. **[blocker]** The new CHECK constraint `chk_notification_mute_category` has no test case, so `pnpm test:int` (a CI gate) goes red if the spec is implemented exactly as written.
   - Bukti: tests/integration/platform/check-constraints.test.ts:4 says "Tabel kasus WAJIB mencakup persis semua `chk_*` di migration.sql". Lines 319-336 scan every migration.sql for `ADD CONSTRAINT `chk_...` CHECK` and assert deepEqual against ALL_CASES (:295). They also compare against information_schema.CHECK_CONSTRAINTS. Spec §3 adds `chk_notification_mute_category`, but §7 never mentions check-constraints.test.ts or check-cases.ts.
   - Perbaikan: Add a case to the ALL_CASES table in §7. Insert `prisma.notificationMute.create({ data: { userId: fx.admin.id, category: 'SYSTEM' } })` and expect errno 4025 on `chk_notification_mute_category`. Insert FINANCE and expect it to pass. The fixture already has `admin` (check-fixture.ts:37,89). Alternatively drop the CHECK, since zod and rules.ts already block SYSTEM.
2. **[major]** In the approved batch order, B1 and A1 land before N2 and N4 lands after it. The spec still hardcodes today's category list, ENUM SQL, hints and broadcast set, and leaves the ATTENDANCE category as an open question.
   - Bukti: The batch order is A1, A2, B1, A3, N1, N2, N4, N3, N5. N5-attendance-reminders.md:3 confirms N5 is last, after N3. Spec §9 says "N4 and B1 will add admin broadcasts" in the future tense. Spec §3 hardcodes `ENUM('ACADEMIC',...,'SYSTEM')`. §4 fixes ADMIN_MUTABLE_CATEGORIES to [FINANCE, STUDENT_AFFAIRS]. CATEGORY_HINTS.STUDENT_AFFAIRS = "Pengajuan izin/sakit baru dari siswa." These break in two cases. (a) If B1 or A1 add a notifySchoolAdmins broadcast mapped to STUDENT_AFFAIRS (as ATTENDANCE_CORRECTED is, rules.ts:23), the hint becomes false and muting Kesiswaan silently mutes anomaly alerts. (b) If B1 appends a NotificationCategory, the N2 CREATE TABLE ENUM is stale. Open question §10.4 (ATTENDANCE category) is decided by N4, which runs in this same batch.
   - Perbaikan: Add `SCHOOL_ADMIN_BROADCAST_TYPES` as a const tuple in notifications/rules.ts, re-derived at implementation time from every notifySchoolAdmins caller, including those added by A1 and B1. Type `notifySchoolAdmins` so that `event.type` must be in that tuple, which forces a typecheck decision for each new broadcast. Add a node:test that checks ADMIN_MUTABLE_CATEGORIES equals the categories of those types minus SYSTEM, and that every hint describes those types. In §3, say to copy the ENUM list from the latest migration that touched NotificationCategory, as N5 does, and to keep N2's migration timestamp after any migration merged before it. Settle §10.4 with the N4 spec now.
3. **[major]** Letting the primary admin edit its own record via `/school/admins/{id}/notification-preferences` contradicts PLAN.md, and the spec never updates that paragraph. PLAN wins per CLAUDE.md.
   - Bukti: docs/PLAN.md:161 says "Admin utama sendiri hanya diubah super admin (403 `PRIMARY_ADMIN_PROTECTED`)" for `/school/admins*`. school-admins/schemas.ts:48 describes isPrimary as "tidak bisa diubah lewat endpoint ini". contracts.ts:22 TARGET_NOTE says the same. Spec §2/§5 skips `manageableTarget` on purpose and integration test 2 expects 200 for the primary admin's own id. Spec §8 only edits the notifications paragraph (:226-231) and Ditunda.
   - Perbaikan: Preferred: on the school route use `manageableTarget` (extra admins only, primary -> PRIMARY_ADMIN_PROTECTED). The primary admin uses `/me/notification-preferences`. This also drops the super-admin-sets-primary path, which nobody needs. Otherwise, explicitly update PLAN.md:157-163, the isPrimary description and the contract description to document the exception.
4. **[minor]** `SecurityCard` and `DEMO_MESSAGE` are not exported today. Importing them as specified creates an import cycle.
   - Bukti: security-panel.tsx:15 is `const DEMO_MESSAGE` and :27 is `function SecurityCard`; neither is exported. security-panel.tsx:6 imports action-dialog, and action-dialog.tsx:9 imports fields. Spec §6 has fields.tsx:42 import NotificationCategoriesField from notification-prefs.tsx, which imports security-panel. That gives the cycle fields -> notification-prefs -> security-panel -> action-dialog -> fields.
   - Perbaikan: Put `NotificationCategoriesField` in its own file, `src/components/hub/notification-categories-field.tsx`, depending only on rules and labels. Move `SecurityCard` and `DEMO_MESSAGE` into a small exported module, e.g. `security-card.tsx`, that both panels import.
5. **[minor]** The planned `format.ts:34` change (empty array -> "—") never touches mutedCategories. It is also a global behaviour change with no benefit.
   - Bukti: In the detail dialog, arrays count as nested values, so `Details` renders them itself. An empty array shows "Belum ada data." (data-view.tsx:26-31) and never reaches `display()`. mutedCategories is not a table column: VIEW_COLUMNS['/school/admins'] is [name,email,isPrimary,isActive,lastLoginAt] (workspace-rules.ts:213). So the detail reads "Kabar yang dimatikan: Belum ada data.", which is wrong copy.
   - Perbaikan: Drop the format.ts change and the `display([])` test. Show an explicit empty state for this field instead, e.g. special-case mutedCategories in Details: "Tidak ada — semua kabar dikirim". Or expose a derived summary string through `prefsSummary`.
6. **[minor]** The row action "Atur notifikasi" loses the planned feedback: the hint is never rendered and the toast is generic.
   - Bukti: action-dialog.tsx:89 renders ACTION_LABELS[...].hint only when `!op.body`. This operation has a body, so the hint "Pilih kabar sekolah yang dikirim ke akun ini." never shows. On success, :79 always toasts "Perubahan berhasil disimpan." instead of `prefsSavedMessage`, which breaks the owner's short cause->effect rule.
   - Perbaikan: Keep the footnote inside `NotificationCategoriesField` so it shows in both places. In ActionDialog, special-case `op.id === 'updateSchoolAdminNotificationPreferences'` to toast `prefsSavedMessage(result.mutedCategories)`. Or drop the unused `hint`.
7. **[minor]** The SchoolAdmin DTO is not normalised, so a stale stored category fails response validation in test mode and shows up raw in the UI.
   - Bukti: Spec §2 adds `notificationMutes: { select: { category: true } }` to ADMIN_SELECT and `mutedCategories` to schoolAdminSchema, which is typed with `mutableCategory`. Only `readNotificationMutes` runs `normalizeMutedCategories`. §9 says stale values are "ignored, hidden by normalize", but `toSchoolAdminDto` (queries.ts:26-40) would pass them through.
   - Perbaikan: State that `toSchoolAdminDto` maps `normalizeMutedCategories(row.notificationMutes.map(m => m.category))`. Add a unit or integration assertion for this.
8. **[minor]** The fallback only counts `isActive`, so a dormant account can absorb a work item and the item still goes silent. The spec calls this its biggest risk.
   - Bukti: In spec §5, `schoolAdminRecipients` filters only `isActive: true`. Example: P mutes FINANCE to delegate to a new treasurer account B. B still has `mustChangePassword=true`, `lastLoginAt=null` or an expired `tempPasswordExpiresAt`. PAYMENT_SUBMITTED then reaches only B, and the fallback never fires because a candidate remains.
   - Perbaikan: In `selectBroadcastRecipients`, treat accounts that have never logged in or whose temporary password has expired as unreachable when deciding whether to fall back. Pass `reachable: boolean` in BroadcastCandidate and add a node:test case.
9. **[minor]** When the primary admin changes another admin's notification settings, the target is not told. The only trace is the audit log.

   - Perbaikan: Return `updatedBy` and `updatedAt` in NotificationPreferences, read from the latest `user.notification_mutes` audit entry. The card can then say "Diatur oleh <nama> pada <tanggal>". Or notify the target when actor ≠ target, using a SYSTEM-category type appended at the END of NotificationType and coordinated with N4/N5.
