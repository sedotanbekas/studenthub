# Kritik adversarial — A1-late-reason

Verdict: Not ready to execute as written. If implemented exactly as specced, `pnpm test:int` goes red because the new `chk_attendance_late_reason` has no entry in the CHECK-constraint coverage table. Three more issues need a decision before coding: (1) the `lateReasonBlock` order contradicts the spec's own integration tests and §9; (2) the note length is counted in UTF-16 while the CHECK counts code points, so some valid-looking input returns 500; (3) the count/display rules are unclear for ADMIN-sourced TERLAMBAT rows, and A3 inherits that. The rest of the design holds up against the code. Every §2 path:line reference checks out against `HEAD` 0cd1d97. Precheck already returns `wouldBeLate` from the same `computeLateness`. Corrections never touch the new columns. The lock order AppLock → Attendance → AuditLog fits `src/lib/tx.ts:7-13`. Tenancy goes through `findFirst({…, schoolId})`. The test helpers exist: `createWorld`/`checkInBodyAt`/`localInstant` at `tests/integration/attendance/checkin/fixtures.ts:48,120,164`, `callRoute` at `tests/integration/helpers/request.ts:88`, and `holdTx`/`raceWhileHeld` at `tests/integration/academics/helpers.ts:68,107`. The working tree currently has uncommitted A1 work from another session; all line numbers below refer to `HEAD`.

1. **[blocker]** `chk_attendance_late_reason` has no case in the CHECK coverage table, so `pnpm test:int` (a CI gate) fails.
   - Bukti: tests/integration/platform/check-constraints.test.ts:4 says "Tabel kasus WAJIB mencakup persis semua `chk_*` di migration.sql". Lines 319-328 scan every migration.sql with `/ADD CONSTRAINT `(chk_[a-z0-9_]+)` CHECK/g` and run `assert.deepEqual(tested, declared)` against `ALL_CASES` (:295-302). Lines 330-336 compare the same list with `information_schema.CHECK_CONSTRAINTS`. Spec §3 (:84) matches that regex. Spec §7 test 9 puts the only CHECK test inside `late-reason.test.ts`, and the spec never mentions `check-cases.ts` or `check-constraints.test.ts`.
   - Perbaikan: Add a case to `attendanceCases` (tests/integration/platform/check-cases.ts:65) using the existing `attendance()` helper (:34-45, default source ADMIN). Violations: OTHER + note null + `lateReasonAt` set; OTHER + `"abcd"`; TRANSPORT + `lateReasonAt` null; category null + note `"x"`; category null + `lateReasonAt` set; OTHER + `"🙏🙏🙏"` (see finding 3). Valid rows: TRANSPORT + `lateReasonAt`; OTHER + `"Ban bocor"` + `lateReasonAt`. Drop test 9 from `late-reason.test.ts` or keep it as an extra. B1 (`chk_attendance_anomaly_review`) and N2 add cases to the same table, so expect merge conflicts there.

2. **[major]** The `lateReasonBlock` order contradicts the spec's own tests and edge-case table. As written, the "correction locks the reason" path is unreachable for most corrections.
   - Bukti: §4 (:109) gives the order `status!==TERLAMBAT -> NOT_LATE` before `source!==CHECKIN -> LOCKED`, and the unit list (:145) asserts `HADIR/ADMIN → NOT_LATE`. But integration test 5 (:312) expects "admin correction to HADIR → 409 LATE_REASON_LOCKED". §9 (:355) says "Any admin correction | LOCKED". Race test 8 (:315) expects LOCKED, which only happens if the held correction keeps TERLAMBAT. A B1 "Tidak valid" review (correction to ALPHA, source ADMIN) would show the student "Absensi hari ini tidak tercatat terlambat, jadi alasan tidak diperlukan" (:185), which is misleading after their late check-in was invalidated. Test 4 (:308-311) also contradicts itself: its heading says NO_ATTENDANCE_TODAY, its first bullet says ATTENDANCE_NOT_LATE.
   - Perbaikan: Check the source first. TERLAMBAT can only have source CHECKIN or ADMIN, because init migration :1068-1071 forces AUTO_ALPHA→ALPHA and LEAVE→IZIN/SAKIT. So: `null/date≠today → NO_RECORD; source === "ADMIN" → LOCKED; status ≠ TERLAMBAT → NOT_LATE; else null`. Change the unit case to `HADIR/ADMIN → LOCKED`, keep tests 5 and 8, and rewrite test 4's heading. Alternative: keep the rule, change tests 5/8 and §9 to 422 ATTENDANCE_NOT_LATE, and make that message mention a correction.

3. **[major]** The note length is counted in different units in JS and in the database. An OTHER note made of emoji passes zod/rules but violates the CHECK, and the API returns 500 INTERNAL_ERROR.
   - Bukti: The CHECK uses `CHAR_LENGTH(lateReasonNote) >= 5` (spec :87). The tables are utf8mb4 (init migration :35), so CHAR_LENGTH counts code points. The rules/zod use JS string length, which counts UTF-16 code units. The spec's own §9 (:359) notes this for `max` ("stricter than the DB limit") but misses that it runs the other way for the minimum. Example: OTHER + `"🙏🙏🙏"` has JS length 6 (passes ≥5) but CHAR_LENGTH 3 (fails). A CHECK violation is not mapped by `mapPrismaError` (src/lib/http/prisma-errors.ts:12-27). It becomes a 500 and is logged as `check.violation` (src/lib/http/route.ts:154-158), which prisma-errors.ts:29-33 describes as "bug: validasi aplikasi terlewat". The textarea counter (`n/200`) would also disagree with VARCHAR(200), which counts characters.
   - Perbaikan: In `late-reason-rules.ts`, count code points (`[...note].length`) for both the minimum of 5 and the maximum of 200, and use the same function for the UI counter. Add unit cases: 3 emoji → problem, 5 emoji → ok. Also strip `\p{Cf}` (bidi overrides such as U+202E, zero-width characters) in `normalizeLateReasonNote`, not only control characters. This text is displayed to admins.

4. **[major]** The count and display rules for ADMIN-sourced TERLAMBAT rows are inconsistent. The PLAN text the spec proposes is false, and A3 inherits the same numbers.
   - Bukti:
     - A correction that keeps TERLAMBAT and changes only `lateMinutes` becomes `source=ADMIN`, still TERLAMBAT (correction-rules.ts:89-94). The reason survives and `lateReasonGroups` (spec :209, `status: "TERLAMBAT"` only) still counts it as filled. That contradicts the PLAN bullet in §8 (:341): "a correction keeps the reason but it is no longer counted".
     - Rows an admin creates as TERLAMBAT (correction-service.ts:74-78) count as `unfilled`, yet the student can never fill them (LOCKED). `lateReasonAdminView` returns `null` for exactly these rows (spec :156), so the detail shows nothing while the counts say "Belum diisi". The monitor fixtures create only ADMIN rows (tests/integration/attendance/monitor/fixtures.ts:82-99), so the planned count tests would lock in that behaviour.
     - Corrections never touch `checkInAt` (correction-rules.ts:7). A row corrected to HADIR therefore renders "Hadir · 07:31 · Hujan / cuaca" in the table cell (data-view.tsx:15, spec :260), because the brief sends the reason "whenever stored" (:219) and the cell has no status guard.
     - A3 counts reasons on all TERLAMBAT rows the same way (A3-monthly-recap-export.md:79).
   - Perbaikan: Pick one definition and write it into §1/§5.2/§8 and A3. For example: `groupBy(["source","lateReasonCategory"])`. `filled` = TERLAMBAT rows with a category, any source. `unfilled` = TERLAMBAT ∧ CHECKIN ∧ no category. Admin-entered TERLAMBAT rows without a reason are either reported separately (`notApplicable`) or excluded. Reword PLAN as "dihitung selama status tetap TERLAMBAT". In every admin surface (table cell, map tag, detail), render through `lateReasonAdminView`, so a reason on a non-TERLAMBAT row always shows as "(sebelum dikoreksi)". Add count cases for TERLAMBAT→TERLAMBAT corrections and for admin-created TERLAMBAT rows.

6. **[minor]** Collision with A3: the edit window, the counting function and the day boundary all differ.
   - Bukti: A1 allows edits until local midnight ("today", spec :179). A3 treats a day as final once `closedThrough` passes, which happens at `dayEndMinute` (auto-alpha-rules.ts:49-52; A3 :113,177). So a "final" recap or Excel can change between, for example, 15:00 and 23:59. The spec says to export `lateReasonGroups` "for A3" (:209), but A3 reads rows with `findMany` and counts in its own single tally (A3 :7,200). The A1 endpoint also counts today's open day; A3 does not.
   - Perbaikan: Make `canEditLateReason` false once `local.minuteOfDay >= dayEndMinute`, so a closed day is frozen. The today DTO already has `school.dayEndMinute` and the PUT can use the same check. Update the copy "bisa diisi nanti hari ini" to match. Drop the "export for A3" claim, or have A3's tally use `countLateReasons` for the category part. State in the endpoint description whether today is included.

7. **[minor]** The default range for `GET /school/attendance/late-reasons` rejects a query that has only `to`.
   - Bukti: Spec :212 calls `resolveRange(query.from ?? monthRange(today.slice(0,7))!.from, query.to, today, 31)`. With `to=2026-09-30` on 2026-10-03, `from` becomes 2026-10-01 > `to`, so `resolveRange` returns null (attendance-stats.ts:168-171) and the request gets a 400 "Rentang tanggal tidak valid". In the generic "Data lengkap" filter panel it is natural to fill in only "Tanggal akhir".
   - Perbaikan: Default `from` to the start of the month that contains `query.to ?? today`. Add a test: only `to` = last day of the previous month → that whole month.
