# Kritik adversarial — B1-anomaly-review

Verdict: Not ready to execute. Implemented exactly as written, two items turn the CI gate red: two response keys have no label, so `pnpm test:unit` fails, and the "Sunday" integration case runs on a fixture school where Sunday is a school day, so `pnpm test:int` fails. Two majors must also be fixed first. (a) A review silently covers flags the admin never saw, and that defeats the "reopen on new flag" rule for SHARED_DEVICE. (b) The new `RecordHost` can open Koreksi with a hidden, wrong date. The core design is sound and matches the code. The lock order AppLock → Student → Attendance follows src/lib/tx.ts:8. Every read and write is tenant-scoped with `findFirst({ id, schoolId })`. `buildCorrectionPatch`/`validateCorrection` are reused unchanged. Audit and notification are written last in the same transaction. The CHECK can never evaluate to NULL: every branch is IS [NOT] NULL, `<=>`, or the NOT NULL `hasAnomaly`. The FK without an explicit index follows init :796. The separate sweep statement is justified. Almost every path:line reference matches HEAD 0cd1d97. These all check out: `assertCorrectableDate` :59-70, `lockRows` tx.ts:113, `attendanceLockKey` lock-keys.ts:56, `lockStudentRow` records.ts:94, `attendanceCorrectedNotification` :47-54, `flagSharedDevice`/`lockSharedDeviceRows` :304-326, `checkInRow` jobs/fixtures.ts:118, monitoring.test.ts:145 (`?anomaly=unreviewed` → 400 today), and the reachability test :90-105, which still passes. The demo arithmetic holds: today d41, d23 and d20 are anomalies; d20 becomes VALID, d24 gains FACE_NOT_DETECTED (MEDIUM), so the count stays at 3.

3. **[major]** A review applies to whatever flags the row has at write time, including flags added after the admin opened the dialog. A SHARED_DEVICE (HIGH) flag can be approved without anyone seeing it, and it never reopens.
   - Bukti: The body is only `{decision, note}` (§5.1). `applyReview` re-reads under lock and writes. While the dialog is open, flags can still be added to an unreviewed row in two ways: another student's check-in (`flagSharedDevice`, src/lib/attendance/check-in-service.ts:318-326), or the day-close sweep (sweep.ts:21-40). VALID then covers a flag the admin never saw. Reopening can never happen afterwards: both writers skip rows that already contain SHARED_DEVICE (check-in-service.ts:320, sweep.ts:39), and the spec's reopen condition requires `NOT JSON_CONTAINS`. §9 (:407) accepts this because "the audit snapshot records which flags were actually reviewed", but that premise is false. The snapshot is `parseFlags(anomalyFlags)` at write time (§5.1 step 4), so it includes the unseen flags. This is the "fingerprint" lesson §9 cites from HRIS. It is most likely between 06:00 and 07:30, when admins review while students are still checking in.
   - Perbaikan: Add `flags: z.array(z.enum(ANOMALY_CODES)).max(ANOMALY_CODES.length)` to the body: the codes the panel showed (`RecordDetailDto.flags[].code`). Add a pure `sameFlagSet(stored, seen)` to anomaly-review-rules.ts, with node:test cases. On mismatch, throw 409 `ANOMALY_FLAGS_CHANGED` "Catatan pemeriksaan berubah sejak dibuka. Periksa lagi, lalu putuskan." Register it in error-status.ts and the contract's `errors`. The panel then reloads, as it does for ANOMALY_ALREADY_INVALID. Do **not** use `updatedAt` as the fingerprint: A1's late-reason PUT (A1 §5.1 e) and corrections touch the same row, which would cause false conflicts. Apply the same check in `applyDemoReview`. Add an integration case: a flag added between GET detail and POST → 409, nothing written. Rewrite the §9 row.

4. **[major]** `RecordHost` can prefill Koreksi with the wrong date for "Data lengkap" daily rows, and the admin cannot see that date.
   - Bukti: In §6, `RecordHost({target, date, …})` opens `ActionDialog op=correctStudentAttendanceDay initial={{studentId, date}}`. For daily rows the date comes from `attendanceTargetOf(row, filterDate)` ("daily row → fallback date"). Daily rows carry no date (`MonitorDailyRow` = `{student, attendance}`, monitor-schemas.ts:176-178). The real date is the Workspace's own `filters.date` (workspace.tsx:29), and the planned `recordDialog({row, viewPath, onClose, onChanged})` signature does not pass it. `AttendanceMonitorPage` can therefore only use the map tab's `filter.date` (attendance-monitor-page.tsx:22), which is separate state. Example: map on yesterday, Data lengkap on today. ActionDialog hides any path parameter present in `initial` (action-dialog.tsx:85), and its heading shows only "Koreksi absensi siswa" (:86, workspace-rules.ts:53). The admin changes the status and the student is notified for a date the admin never saw.
   - Perbaikan: Take studentId and date from the loaded detail, not from props: `onCorrect(detail)` → `initial={{ studentId: detail.student.id, date: detail.date }}`. Keep the `date` prop only for the demo loader (`useRecordDetail`). Add a test that the Koreksi prefill comes from the detail. Optionally show the date as fixed text in the correction dialog.
