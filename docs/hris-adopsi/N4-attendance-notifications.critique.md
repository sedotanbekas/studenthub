# Kritik adversarial — N4-attendance-notifications

Verdict: Needs revision before implementation. Nothing here turns the CI gate red, but two majors must be settled first. (1) As specified, any day on which nobody could check in pushes "Kamu tercatat Alpa" to every student who has ever logged in. That covers an unentered or wrongly removed holiday, a school that does not take attendance in the app, and a check-in outage. Retraction only removes the inbox row; the push has already gone out. (2) The category question has to be decided now, because N2 ships first and its hint and broadcast typing become wrong under the spec's default. The core design holds up against the code. There is one close path (`closeDayLocked`), notifications are written in-transaction, and the drafts shape (`source`, `studentId`) matches. `(userId, dedupKey)` with nullable keys behaves as claimed. The ENUM list is exactly the current one: init migration :283, untouched since, and A1/B1/N2 add no NotificationType. `MODIFY … ALGORITHM=INSTANT` that appends at the end is valid on MariaDB 10.11 (1-byte ENUM, table utf8mb4_unicode_ci, init :305). Stale re-closes (calendar sync, >7 days) never notify. Every cited path:line checks out at HEAD 0cd1d97; the uncommitted A1 work in the tree shifts `demo.ts:66` to :69.

1. **[major]** Days with no check-ins trigger a mass false "Kamu tercatat Alpa" push. The spec's "withdraws the notices" does not undo a delivered push.
   - Bukti: `planDayClose` writes ALPHA for every eligible student without a row (auto-alpha-rules.ts:152-160). On a holiday that is missing from the calendar, nobody checks in, so every student becomes ALPHA. Entering holidays after the fact is a supported flow: school admins may backdate holidays 7 days (PLAN.md:176, calendar/rules.ts:33), and the sync deletes ALPHA rows when a holiday is ADDED (calendar-sync.ts:155-156). Removing a wrongly entered holiday is worse. Check-in was blocked that day (decideCheckIn checks holidays, PLAN.md:186), so after `reopenRecentDays` (calendar-sync.ts:95-104, for a national holiday every active school at :125) the tick re-closes the day and every student becomes ALPHA. Under N4 each of these cases sends one PENDING push per logged-in student. The next tick's `push-dispatch` delivers them, because tick order is push-dispatch first, then auto-alpha (PLAN.md:256), and dispatch.ts:77-91 claims the rows. `retractDayNotices` later deletes only the inbox row. A push already on the lock screen cannot be recalled, and no correction is sent. A school that is live for billing or report cards but not yet for app check-in gets the same false push every school day for each logged-in student. Spec §9 does not list this risk.
   - Perbaikan: Add a pure rule in `day-notice-rules.ts`, e.g. `holdAlphaNotices(c: { checkins: number; alpha: number }): boolean`. It returns true when the closed day has 0 CHECKIN rows. Optionally also hold when the CHECKIN share is below a named threshold, decided by the owner. Get the count from the same `groupBy` extended with `source`, or from one `count({ schoolId, date, source: "CHECKIN" })`. When it holds, send no student notices, but still send the admin summary with one extra cause→effect line next to the CTA, for example: "Belum ada siswa yang absen lewat aplikasi pada tanggal ini — notifikasi Alpa ke siswa ditahan. Libur? Tambahkan di Kalender." Add node:test cases (0 check-ins → hold; 1 → send) and an integration case: a day with only ALPHA rows gives students 0 notices and admins a summary with the hold line. Add this as owner question 6 and to §9.

2. **[major]** The category must be decided now, because N2 lands first. The default (STUDENT_AFFAIRS) silently breaks N2's own copy and couples a daily recap to a work queue.
   - Bukti: N2 §4 fixes `CATEGORY_HINTS.STUDENT_AFFAIRS = "Pengajuan izin/sakit baru dari siswa."`. With N4's default, muting "Kesiswaan" also mutes the daily recap, so the hint becomes false. The N2 critique (#2) asks to settle N2 §10.4 together with N4. It also proposes typing `notifySchoolAdmins` by a `SCHOOL_ADMIN_BROADCAST_TYPES` tuple, plus a test that every hint describes those types. N4 §2 says "Reused as-is. N4 adds no preference logic", which would then fail typecheck and that test. N2 §9 names a silenced work item as "the biggest risk", and its primary-admin fallback fires only when *every* admin mutes (N2 §4 `selectBroadcastRecipients`). A teacher account that mutes Kesiswaan to drop one daily FYI therefore also stops receiving `LEAVE_SUBMITTED`. N2 demo persona "Pak Dodi (Guru BK)" is exactly the account that wants the Alpa recap but not the leave queue. Today all attendance/leave types are STUDENT_AFFAIRS (notifications/rules.ts:10-12,23). Announcements use an explicit category list (announcements/constants.ts:15; schemas.ts:118), so a new category does not leak into the announcement form.
   - Perbaikan: **Rekomendasi: add a new `ATTENDANCE` ("Kehadiran") category for `ATTENDANCE_DAY_SUMMARY` only, and keep `ATTENDANCE_ALPHA` in STUDENT_AFFAIRS.** The alpha notice is personal, never filtered, and matches `ATTENDANCE_CORRECTED`/`LEAVE_*` in the student inbox. Append the value in **N2's** migration (20261003030000), not N4's: MODIFY at the end of `Notification.category` and `Announcement.category` (both instant), and create `NotificationMute.category` with it from the start. N4 then needs no category DDL. Also in N2: add the `ENUM_LABELS.NotificationCategory.ATTENDANCE` label, but keep ATTENDANCE out of `ADMIN_MUTABLE_CATEGORIES` until a broadcast uses it. In N4: set `CATEGORY_BY_TYPE.ATTENDANCE_DAY_SUMMARY = "ATTENDANCE"`, add ATTENDANCE to `ADMIN_MUTABLE_CATEGORIES` and the broadcast-type tuple, and set `CATEGORY_HINTS.ATTENDANCE = "Rekap kehadiran harian: Alpa, terlambat, anomali."`. Change rules.test (the summary maps to ATTENDANCE) and integration test 7 (mute ATTENDANCE; muting STUDENT_AFFAIRS no longer drops the recap). Close N2 §10.4 and N4 §10.1 with this decision. If the owner keeps STUDENT_AFFAIRS, as the original task said, N4 must still edit N2's hint to "Pengajuan izin/sakit baru dan rekap kehadiran harian." and add the summary type to N2's broadcast tuple and test.

3. **[minor]** Retraction misses cases and does not scale on the national path.
   - Bukti: (a) Retraction keys only on removed **AUTO_ALPHA** rows (spec §5). A pending-variant notice ("…karena pengajuan sakit kamu belum disetujui") whose row was later converted to LEAVE on approval (materialize.ts:68-69) is removed as `source: LEAVE` (calendar-sync.ts:35). Its Alpa notice for what is now a holiday stays. (b) The summary is retracted only for "affected schools", meaning schools with removed rows. A date whose rows were all CHECKIN/ADMIN still keeps "Rekap kehadiran …" for a holiday. (c) The spec accumulates `{id, schoolId, studentId, date, source}` across **all** 50-school chunks and retracts after the loop. On a retroactive national holiday that can mean one row per student platform-wide, held in memory, followed by chunked userId lookups inside the 60 s holiday transaction (holiday-service.ts:141). Today the loop holds only one chunk's ids (calendar-sync.ts:72-79).
   - Perbaikan: Retract per school chunk. For each chunk, take the studentIds of removed rows of **either** derived source, map them to userIds, and run `deleteMany({ type: "ATTENDANCE_ALPHA", userId: { in }, dedupKey: { in: dates.map(alphaNoticeKey) } })`. Delete the summary for every school in the chunk on the deleted dates, whether or not it had removed rows; a national holiday covers all schools anyway. Return the counts only. Add test cases for (a) and (b).

4. **[minor]** The idempotency rationale is partly wrong, and INSERT IGNORE swallows more than duplicates.
   - Bukti: Transactions run at READ COMMITTED (tx.ts:19-23,27). A concurrent closer's committed AUTO_ALPHA rows are therefore visible to the re-query in §5 step 2, so the claim that it "drops drafts that … another writer got there first" is false. The `dedupKey` unique index is what de-duplicates; the re-query only drops rows that check-in, leave or correction wrote. The codebase's own justification for IGNORE depends on rows that cannot fail other constraints (auto-alpha-job.ts:105-108). On MariaDB, IGNORE also turns truncation and invalid-ENUM errors into warnings, and FK errors as well. `notify.ts:38-39` bounds only title and body, not the key. A key over 64 characters is silently truncated, and two different keys can then collide, so a notice is dropped. A type value missing from the DB ENUM (for example, N5 mis-copying N4's list, N5 §3) is stored as `''` instead of failing, and that row then breaks Prisma reads of that user's inbox.
   - Perbaikan: Fix the §5 text: the re-query filters CHECKIN/LEAVE/ADMIN winners, and `dedupKey` handles concurrent closers. Add `NOTIFICATION_DEDUP_KEY_MAX = 64` next to `NOTIFICATION_TITLE_MAX` and make `notifyRecipients` throw when a key exceeds it, with a unit test. Keep an integration assertion that reads both new types back through `toInboxItemDto`, so a broken ENUM list fails CI. Write the index as `ALTER TABLE \`Notification\` ADD UNIQUE INDEX … , ALGORITHM=INPLACE, LOCK=NONE` so that a large Notification table can never fall back to a silent COPY. If N2 adopts its critique #9 (a new SYSTEM type), copy the ENUM list from that migration.

Integration test 5 needs a `hasAnomaly` row, but today `checkInRow` forces `hasAnomaly: false` (tests/integration/attendance/jobs/fixtures.ts:139). B1 adds the option.
