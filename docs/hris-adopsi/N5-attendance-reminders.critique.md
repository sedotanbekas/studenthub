# Kritik adversarial — N5-attendance-reminders

Verdict: Not ready to execute. Implemented as written, the missing case for `chk_school_reminder_lead` turns `pnpm test:int` red. Three majors need fixing first. (a) The owner question "default ON?" would be settled by the auto-merge-to-production workflow before the owner answers, and it would also cover schools still on the untouched default schedule. (b) "Expires at the bell" is enforced only inside the dispatcher: the push transports keep the message up to 60 minutes. (c) The integration tests cannot pass, because every `addDevice` session has already expired at the fixed 2031 instant. The core design is sound and matches the code: one JobRun per (school, local date) with a batched settled pre-check, the mask/WIT window computed with `localParts`, the hidden PENDING+read row (`unreadCounts` and N3's badge both filter `readAt: null`), N2 mutes that never touch `notifyRecipients`, N3's PENDING-for-all-roles, and the check-in OBSOLETE update written last in the same transaction. The post-insert sweep works because `withTx` defaults to READ COMMITTED (src/lib/tx.ts:19-24,27). The ENUM list matches the current schema plus N4. Nine path:line references are wrong.

1. **[blocker]** The new CHECK `chk_school_reminder_lead` has no test case, so the CHECK coverage test fails.
   - Bukti: Spec §3 (N5-attendance-reminders.md:62) adds `ALTER TABLE School ADD CONSTRAINT chk_school_reminder_lead CHECK (...)`. §7 (:149-170) never mentions the CHECK tests. tests/integration/platform/check-constraints.test.ts:4 says the case table MUST cover exactly every `chk_*`. Lines 319-336 regex-scan every migration.sql for `ADD CONSTRAINT \`chk_...\` CHECK`, deepEqual the result against ALL_CASES (:295-302), and compare it with information_schema.CHECK_CONSTRAINTS. SCHOOL_CASES (:59-118) has no entry for the new constraint.
   - Perbaikan: Add to SCHOOL_CASES in §7: violations `updateSchool({ attendanceReminderLeadMinutes: 4 })` and `updateSchool({ attendanceReminderLeadMinutes: 121 })` (helper at :45); valid `createSchool({ data: { attendanceReminderLeadMinutes: 120 } })`. The alternative is to drop the CHECK, since zod already enforces 5..120.

2. **[major]** The open owner question "default ON for existing schools" (§10.1) becomes production behaviour without an answer. It also reaches schools that never configured their bell time, and no admin is told.
   - Bukti: §10.1 (:205) and §9 "Biggest risk" (:194) leave the default at ON. HANDOFF.md:47-51 says each feature is committed, fast-forwarded and pushed "tanpa bertanya dulu", and that a push to master is a production deploy. The migration (:60) therefore turns reminders on at every live school from the next school day. Many schools may still run the seeded schedule: onboarding-rules.ts:61,76-81 treats the untouched default as "optional" ("Masih bawaan"), and the defaults are open 06:00 / start 07:00 (prisma/schema/school.prisma:64-65). Students at those schools would get "Jam masuk pukul 07:00" (:94) for a bell time the school never confirmed. The PUT writes no notification (:106) and the card only lives inside Pengaturan sekolah (:130), so admins hear about the feature from students first.
   - Perbaikan: Ask the owner Q1 explicitly before merging N5; the earlier features do not depend on it. Without an answer, ship `attendanceReminderEnabled BOOLEAN NOT NULL DEFAULT false` (Prisma `@default(false)`), and set it true explicitly in platform school creation if the owner wants it on for new schools. Add a `schoolSetupSteps` item "Pengingat absen" (optional, CTA `/hub/school-settings`). If the owner chooses ON, still skip schools whose schedule equals `DEFAULT_SCHOOL_CONFIG`: move `isDefaultSchedule` from onboarding-rules.ts:61 into a shared pure module and test it.

3. **[major]** `pushExpiresAt` stops sending only inside the dispatcher. After hand-off, the push services keep the message for up to an hour, so "expires at the bell" does not hold on the device.
   - Bukti: §1 (:7) promises the row "expires at the bell". §9 (:186) says retries after the bell become EXPIRED. The only check is `isExpired` before sending (dispatch.ts:60-61). N3 sets the web TTL from `createdAt` only: `webPushTtlSeconds(createdAt, now)` = clamp(3600 − age, 60, 3600) (N3-web-push.md:125,136). N3 :348 claims consistency with EXPIRED, but only for the 60-minute rule. The Expo `PushMessage` has no ttl or expiration field (src/lib/push/types.ts:12-20). Example: a reminder created 06:45 for a phone with data off during the commute is delivered when it reconnects, up to about 07:45. That is after the bell, possibly after the student checked in, and it can no longer be voided, because OBSOLETE only touches PENDING rows (:125).
   - Perbaikan: Pass `pushExpiresAt` from CLAIM_SELECT down to both transports. Web: TTL = min(N3 TTL, floor((pushExpiresAt − now)/1000)), with no 60 s floor when `pushExpiresAt` is set (skip the send if the result is < 1). Expo: `expiration = floor(pushExpiresAt/1000)`. Add cases to `push/web/rules.test.ts` and `push/rules.test.ts`, and update N3 §4/§9.7 to match.

4. **[major]** The integration tests cannot pass as specified: every device created with `addDevice` has expired at the fixed 2031 instant.
   - Bukti: §7 (:153-155) uses fixed 2031 instants (`2031-03-17T23:50Z`) and `addDevice` from tests/integration/push/helpers.ts. `addDevice` (:28-40) calls `createSessionToken` without `now` or `expiresAt`, so `expiresAt = new Date() + 30 days` (tests/integration/helpers/auth.ts:24,30). `loadDevices` filters `expiresAt: { gt: now }` using the job's `now` (src/lib/push/delivery.ts:23), and N3's web loader does the same (N3-web-push.md:202). So `reachable` is always empty and 0 rows are written. The "exactly one row" test fails, and every skip test passes for the wrong reason.
   - Perbaikan: Add an option, e.g. `addDevice(userId, state, { expiresAt })`, or forward `now`. Create devices that expire after the fixed instant (e.g. 2031-04-30). Give every skip test a positive control: a sibling student who does receive a row.

7. **[minor]** Any reminder written in the last minute before the bell is always discarded as EXPIRED before it is sent. For some legal schedules, every reminder ends up that way.
   - Bukti: Step 6 (:122) says "No kick: push-dispatch sends on the next tick". Jobs in a tick run concurrently (tick-runner.ts:61), and the dispatcher stops after a short claim (dispatch.ts:86), so rows committed in tick T go out in tick T+1, about 60 s later. The new `isExpired` is `now >= pushExpiresAt` (:31), and the window runs right up to `startMinute` (:80). Rows written in the final minute are therefore never sent. That includes a FAILED retry, the `hasMore` spill-over, and every row for a school with `checkInOpenMinute = startMinute − 1`, which `chk_school_schedule` allows (`open < start`, prisma/migrations/20260921000000_init/migration.sql:1036-1040). With lead ≥ 5 such a school gets `sendMinute = open`, a one-minute window.
   - Perbaikan: End the window one minute early (`sendMinute <= local < startMinute − 1`, and test 06:59 → null). Or call `void kickPushDispatch()` after each school's commit (src/lib/push/kick.ts:16; the dispatcher is single-flight), or do both. If the window becomes empty, the slot is null; cover that case in the tests.

The student card already shows that time as `lateAfter` (student-queries.ts:45). The spec expires the push at `startMinute` (:81), yet the body says "agar tercatat hadir tepat waktu" (:94). A push delayed to 07:05 is dropped even though a 07:05 check-in still counts as on time.

10. **[minor]** The spec ignores N4's dedup mechanism and relies on a non-atomic anti-join for per-student idempotency.
   - Bukti: N4 adds `dedupKey` + `@@unique([userId, dedupKey])` + INSERT IGNORE, and makes it the rule for job-generated notices (N4 :45-49, :204), two migrations before N5. Under READ COMMITTED (tx.ts:19-24) that is a plain read, so it does not stop two writers: the §7 test that calls `sendSchoolReminders` directly, or a manual `jobs:run` racing a takeover. It also forces the whole school into one 30 s transaction (:116).
   - Perbaikan: Give the template `dedupKey: "attendance-reminder:" + date`, drop the `notifications none` clause, and turn the "pre-existing reminder is not duplicated" test into a dedup-key test. Once inserts are idempotent, the job can also commit per 500-candidate chunk.

With VAPID off, reminders are written for web-only students and then end SKIPPED `NO_DEVICE`, and the GET `pushReadyStudentCount` overstates the reach.    - Perbaikan: Export one `reachableUserIds(userIds, now)` from `src/lib/push` that uses the same `web` flag as `processClaim`, and use it in both the job and the GET. Optionally require at least one mobile or standalone subscription for this type.

13. **[minor]** Volume and throughput are not sized. The default creates one burst per time zone, and the hidden rows are kept for a year.
   - Bukti: With lead 15 and the default schedule (school.prisma:64-65), every WIB school's reminders are written in the same tick, and likewise for WITA and WIT. The dispatcher is a single in-process run (queue.ts:10-16) with a 40 s budget (push/constants.ts:22). It claims FIFO by `pushNextAttemptAt` (claim.ts:43-44), so other notifications queue behind the burst. N3's worst case is 25 s per 100 web sends (N3 :208). Check-in requires being inside the geofence (check-in-rules.ts:157-160), so at T−15 the recipients are probably most reachable students, not a forgetful minority. That means close to one hidden row per reachable student per school day, kept 365 days (retention.ts:21), with no `[type, createdAt]` index to purge them early (notification.prisma:130-135). §9 (:191) only defers this to the backlog.
   - Perbaikan: State the expected rows per day and the drain time at the 25 s/100 worst case. Add `@@index([type, createdAt])` now (an additive, online CREATE INDEX) and a short retention for `PUSH_ONLY_TYPES` in `maintenance-daily`, e.g. 30 days. Log `expired` per school in `JobRun.result` so slow drains show up.
