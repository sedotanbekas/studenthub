# Kritik adversarial — N1-badge-polling

Verdict: Needs revision before implementation. There is one blocker: the poller stops for good if the page is hidden and shown again within 5 s of the last poll. There are three majors: the premise behind retrying on 409 REFRESH_RACE is wrong, a 401 stops the poller even when the user is still signed in, and stop/abort leaves state underspecified so logout can still show a false "Sesi berakhir". The rest is solid: every cited path:line checks out, there is no server, schema or OpenAPI change, and tenancy is safe because the endpoint is scoped to the user.

1. **[blocker]** Polling dies permanently after a quick hide/show (tab switch, phone lock/unlock, app switcher glance) within 5 s of the last attempt. No timer is left armed, so the badge silently stops updating until the next visibility/focus/online event.
   - Bukti: Spec §5: 'hidden clears the timer', 'schedule(ms): does nothing while hidden', 'visible, focus and online call run'. Spec §4 decideFetch: visible/focus/online return 'skip' when now - lastAttemptAt < 5 s. run() only describes the fetch branch, so a skip schedules nothing. Trace: poll at t=0 arms a 30 s timer; hidden at t=2 clears it; visible at t=4 is a skip and no timer exists. Switching browser tabs fires visibilitychange but not window 'focus', so nothing recovers it. The same happens when a request completes while hidden (schedule is a no-op) and the page becomes visible less than 5 s after that attempt. Unit test 2 ('hidden clears the timer … visible → immediate fetch') does not cover this path.
   - Perbaikan: Track the due time: add `nextDueAt: number | null` to BadgePollState and keep it when hidden (clear only the OS timer). On visible/focus/online: if no attempt has been made, or the next poll is already due and the last attempt is at least 5 s old, fetch. Otherwise re-arm the timer for `max(nextDueAt, lastAttemptAt + BADGE_MIN_GAP_MS) - now`. In practice decideFetch returns {action, delayMs} instead of a bare 'skip'. Apply the 5 s dedupe only when the last attempt succeeded, so `online` after a network failure fetches right away instead of waiting up to 5 min. Add unit tests: (a) success at t0, hidden at t0+1 s, visible at t0+3 s gives no immediate fetch but exactly one fetch by t0+30 s; (b) result arrives while hidden, then visible within 5 s, still gives a later fetch.
2. **[major]** The 409 REFRESH_RACE retry rests on a wrong premise ('another tab already rotated the cookies'). The retried request can still 401, the proxy wipes the session hint on 409, and the poller then stops on that 401 while the user stays signed in. The result is a badge frozen until the next sign-in, with no message.
   - Bukti: refresh-service.ts:122-147: the losing request gets 409 as soon as the winner's CAS commits, but the winner still has to sign the JWT and return through the proxy before its Set-Cookie reaches the browser. The 409 can arrive first, the retry then sends the old cookie, and the proxy returns 401 WEB_SESSION (route.ts:113). Spec §2 does not say what happens when the retry 401s. Today only !ok dispatches studenthub:expired (api.ts:13-14), so with the spec's change the 401 goes straight back to the caller. Spec §4 classifyPollFailure maps 401 to 'stop', and the poller restarts only on an identity change (§9 row '401/403'). Separately, the proxy calls clearHint for any 4xx refresh including 409 (src/app/api/web/[...path]/route.ts:139), deleting SESSION_HINT. The next full load then renders the login view first (session-hint.ts:20-21) and recovers only through legacySession. The Expo contract itself says '409 → re-read stored token then retry once' (refresh-service.ts:18).
   - Perbaikan: In apiFetch, on refresh 409: wait briefly (e.g. 300 ms, as a named constant) and retry the original request. If that still 401s, run the single-flight refresh once more; only then dispatch studenthub:expired (keep the '/auth/me' exception). Put this in a pure rule `afterRefresh(status, attempt)` with tests. Change the proxy at route.ts:139 to skip clearHint when upstream.status === 409, and record it as a deliberate small server change, since the spec claims none. In badge-poll-rules, make 401 'retry' and keep only 403 as 'stop': a real expiry already reaches the poller through studenthub:expired → setMe(null) → effect stop().
3. **[major]** Stop and abort semantics are underspecified. The spec's own guarantee ('no poll runs against a revoked session' / no false 'Sesi berakhir' on logout) does not hold, and a restart after stop can skip forever.
   - Bukti: (1) apiFetch awaits the shared `refresh` promise, which has no signal (api.ts:12), then dispatches studenthub:expired whenever refresh is !ok (api.ts:13-14), without checking init.signal.aborted. If logout (use-session.ts:163) revokes the session while a poll is waiting on refresh, the refresh 401s and use-session.ts:122 sets 'Sesi berakhir. Silakan masuk kembali.', even though stop() already aborted that poll. (2) The spec bumps `generation` only in start(), not in stop(). It never says stop() resets inFlight, the queued flag, failures or lastAttemptAt. With inFlight left true, start() → run('start') → decideFetch returns 'skip' (in flight), so nothing is fetched or scheduled. failures would also carry user A's backoff over to user B. (3) browserBadgeDeps maps only TypeError to status 0, but an abort rejects with DOMException 'AbortError'. If run() does not catch it, it becomes an unhandled rejection, which existing browser tests count as page errors (expect(errors).toEqual([]) in frontend.spec.ts:35 and others).
   - Perbaikan: In apiFetch, after `await refresh`, if `init.signal?.aborted` then throw an AbortError without retrying or dispatching studenthub:expired. Specify that stop() does generation++, aborts, clears the timer and listeners, and resets the state to {failures:0, lastAttemptAt:null, inFlight:false, queued:false, nextDueAt:null}. run() must return early when stopped, and the queued-mutation replay must check generation too. fetchUnread maps AbortError to a sentinel (e.g. status -1) that the generation check discards. Add unit tests: stop during a pending refresh dispatches no expired event; start(B) after stop() during an in-flight request fetches immediately with failures = 0.
4. **[minor]** Retry-After can never reach classifyPollFailure, and focus/visible triggers bypass it anyway.
   - Bukti: BadgeDeps.fetchUnread returns only {status, body} (spec §5). The proxy rebuilds every JSON response with NO_STORE headers only (route.ts:136), so the upstream Retry-After header is lost. The value survives only in the body as error.details.retryAfterSeconds (src/lib/http/errors.ts:25-26). Unit test 4 ('429 with retryAfterSeconds: 600') feeds an input the real deps can never produce, and the 5 s dedupe lets a focus or visible event fetch inside the Retry-After window.
   - Perbaikan: Add a pure `retryAfterFromBody(body)` that reads error.details.retryAfterSeconds and use it in the controller. Store `nextDueAt = now + retryAfterMs` so the visibility fix above also honours it.
5. **[minor]** Jitter is applied before the 5-minute cap, so every failing client retries at exactly 300 s. After a PM2 restart or deploy outage, which hits all clients at once, retries stay synchronized.
   - Bukti: Spec §4: `min(MAX, round(base × 2^n × jitter))`. At failures ≥ 4 for staff, or ≥ 3 for students, the cap removes all jitter (the test expects exactly 300 000 at failures 4 and 50).
   - Perbaikan: Use `round(min(MAX, base × 2^min(n,10)) × (1 − J + 2J·random))`, then `max(retryAfterMs ?? 0, …)`. Update the tests: failures 4 with random 0 gives 270 000 and random 1 gives 330 000.
6. **[minor]** navigator.setAppBadge is dead weight in N1 and will conflict with N3. It breaks YAGNI and the spec's claim that 'N3 reuses the same badge path'.
   - Bukti: There is no web app manifest: src/app has no manifest.* and public/ contains only brand/demo/models/vendor. The site is therefore not installable, so the Badging API has nothing visible to badge, and iOS needs a manifest-based Home Screen app. The poller pauses while hidden, which is exactly when an icon badge matters. N3 would set the badge from a service worker, which cannot use the page's UnreadBadgePoller. The page caches `last` (appBadgeAction count === last → 'none'), so it will diverge once the service worker changes the badge, and stop() clears a badge the service worker owns.
   - Perbaikan: Remove appBadge from N1: drop appBadgeAction, deps.appBadge, unit test 11 and the doc bullets. Let N3 own the badge together with the manifest and service worker, with the service worker as the single writer.
7. **[minor]** Background 401s are a visible behaviour change, not a 'passive badge'. A revoked session now kicks the user to the login page within 30–60 s even when idle, wiping open dialogs and forms. The spec does not document this.
   - Bukti: Spec §6: 'On error the last known count stays visible and nothing is shown to the user.' A poll 401 → refresh fails → studenthub:expired → setMe(null) plus the 'Sesi berakhir' toast (api.ts:14, use-session.ts:122). Revocation causes that are routine here: a student logging in on another attendance device revokes the other attendance-device sessions (device.ts:8-9), plus logout-all, admin password reset and deactivation. Example: a student's mobile-browser session gets REPLACED and the check-in or leave form vanishes mid-entry.
   - Perbaikan: State this in §6 and §9 and in FRONTEND.md 'Sesi web'. Optionally ask the owner whether to defer the kick while an ActionDialog or the check-in flow is open, for example by having the poller pass a flag so apiFetch skips the dispatch for background requests and lets the next user action handle the expiry.
8. **[minor]** The cost model leaves out two new loads: refresh-token rotation for every visible tab, and log retention under the existing pm2-logrotate limits.
   - Bukti: ACCESS_TOKEN_TTL_SECONDS = 900 (access-token.ts:6). With polling, an idle but visible tab now refreshes every 15 min. Each refresh is a withTx with a CAS update, an AuthSession update and a RefreshToken insert (refresh-service.ts:122-135), which previously happened only on user activity. Each poll also logs one 'request' line (route.ts:162-173). pm2-logrotate keeps 20 MB × 14 files (docs/deploy/BOOTSTRAP.md:126) and rotates by size, so poll lines will crowd out the request logs used for incident debugging (D19, docs/design/05-platform-crosscutting.md:33).
   - Perbaikan: Add both to §2 and §9 with numbers (e.g. 1 000 visible students ≈ 1.1 refresh tx/s). Either skip the 2xx request log for getUnreadNotificationCount now (a tiny server change behind a contract flag) or give the backlog item a concrete trigger tied to log-retention days rather than 'if volume becomes a problem'.
9. **[minor]** The StrictMode and idempotency claims are inaccurate, and dev HMR creates duplicate pollers.
   - Bukti: Spec §9 says 'start is idempotent' handles React StrictMode. But the hook's cleanup calls unreadBadge.stop() between the double mount (spec §6, `return () => unreadBadge.stop()`), so the 'same userId+role & running → no-op' path never runs: StrictMode gives start → stop (abort) → start, i.e. two fetches. Hot-reloading unread-badge.ts in dev builds a new module singleton while the old instance's listeners and timers keep firing.
   - Perbaikan: Rewrite the risk row: in StrictMode the first fetch is aborted and discarded by generation. That is harmless, but say so. For dev, keep the singleton on globalThis (e.g. `globalThis.__studenthubBadge ??= …`) or have the module stop any previous instance on re-evaluation.
10. **[minor]** The new integration test mostly duplicates existing coverage.
   - Bukti: tests/integration/notifications/inbox-read.test.ts:112-128 already checks unread-count dropping after read (5 → 3), and :130-153 checks read-all → total 0. No server code changes in N1.
   - Perbaikan: Drop it, or reduce it to the one new assertion (notify after read-all → total 1) inside the existing read-all test.
11. **[minor]** The approved docs will drift: the contract text still says 30 s for all, and the client-approved PLAN gets implementation tuning written into it.
   - Bukti: contracts.ts:39 ('polling endpoint ini tiap 30 detik') and design D5 (docs/design/05-platform-crosscutting.md:19, 'Staff and sponsor dashboards poll … every 30 s') do not match the 60 s for students. The spec leaves the contract and openapi.json unchanged but rewrites docs/PLAN.md:231 with intervals and backoff values.
   - Perbaikan: Keep PLAN.md:231 a one-line decision ('web: satu poller badge; siswa 60 dtk; Web Push menyusul N3') and put the parameters in FRONTEND.md and D5. Either accept the contract text as staff guidance and say so in §5, or update the description and run openapi:export + openapi:check (catalog.json carries no descriptions, so frontend:sync is unaffected).
